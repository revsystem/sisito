# ダッシュボード全チャートへの日付範囲反映 設計仕様

日時: 2026-08-10
深度: standard

## 目的・コンセプト

sisito のダッシュボード（`/`）にある全チャートを、画面上部の from / to / addresser フォームで指定した集計期間に追従させる。

現状は Recently Bounced セクションの 4 チャート（棒・パイ 2 枚・折れ線）だけが期間フィルタを反映し、Unique Recipient Bounced の 3 チャートと Bounced by Type の reason 別ドーナツ群はテーブル全期間を集計している。同じ画面の中でフォームが効くチャートと効かないチャートが混在しているため、利用者は「先月のバウンス傾向」を見ようとしても下半分が全期間の数字のままで、上下のチャートを突き合わせた解釈ができない。この不整合を解消する。

## 想定利用者と利用シーン

利用者はメール配信のバウンス状況を監視する運用担当者で、実質的にはリポジトリ所有者本人が Raspberry Pi 上のインスタンスを使う。主な利用シーンは、特定期間に発生したバウンスの傾向把握（どのドメイン宛が多いか、どの reason が支配的か、どの送信者が影響を受けたか）と、施策前後の比較である。

最重要前提として、この Pi は `RAILS_ENV=development` で動作しており `cache_if_production` が素通しになるため、ダッシュボードを開くたびに全クエリが実クエリとして走る。キャッシュの挙動は本番相当環境でしか観測できない。

## スコープ

含めること。`StatsController#index` の後半 4 ブロック（`@uniq_count_by_destination` / `@uniq_count_by_reason` / `@uniq_count_by_sender` / `@bounced_by_type`）への期間フィルタ適用と、それに伴うキャッシュキーの変更、および期間を絞った結果データが空になったときのビュー側ガード追加。

含めないこと。フォーム UI 自体の変更（項目追加やプリセットボタン）、`shorten_stats` フラグの挙動変更、後述する `etc` 系列の二重計上バグの修正、新規インデックスの追加。

線引きの根拠は、今回の要求が「既存の期間指定を全チャートに効かせる」ことに閉じており、UI やフラグ設計に踏み込むと検証範囲が広がるためである。`etc` の二重計上は全 6 チャートブロックに存在する既存バグだが、日付範囲とは直交した別問題なので research.md に記録して切り離す。

## アーキテクチャ設計

変更は `StatsController#index`、`BounceMail`（期間 scope の追加）、`StatsHelper`（期間ラベル）、および配下ビュー 2 枚に閉じる。スキーマ・マイグレーション・ルーティングには触れない。

期間の解決は既に `index` 冒頭（stats_controller.rb:3-6）で `@recent_days_from` / `@recent_days_to` / `@addresser` として済んでおり、後半 4 ブロックも同じインスタンス変数を参照できる。新しいパラメータ体系は不要で、Recently Bounced 側と同一の述語を後半へ横展開する構造になる。

述語そのものは論点 1 の回答（B）に従い `BounceMail.within_period(from, to)` として scope に切り出す。モデルへの追加はこの scope 1 つのみで、既存メソッドや関連には手を入れない。

主要な構造判断は、期間述語を「同一の式」として揃えることである。上半分と下半分で境界の扱いが 1 日でもずれると、パイの合計と棒グラフの合計が食い違い、データ不整合として読まれてしまう。

## 技術選定と根拠

新規の依存追加はない。既存の ActiveRecord のリレーション連結と `cache_if_production` をそのまま使う。

述語の重複をどう扱うかは論点 1 で検討し、モデルの `scope` に切り出す案（`BounceMail.within_period`）を採用した。コントローラ内 private メソッドに addresser 絞り込みごと集約する案は、`select` 先行のブロックに合わせる調整が要るため見送っている。

## データ設計

スキーマ変更なし。`bounce_mails` の既存インデックスのうち `idx_timestamp` と `idx_timestamp_addresser` が期間レンジ走査に使われる想定である。集計自体は `destination` / `reason` / `addresseralias` での GROUP BY となるため、レンジ絞り込み後にテンポラリテーブルでの集約が発生する。

## 要件ごとの実装方針

4 ブロックすべてに `BounceMail.within_period(@recent_days_from, @recent_days_to)` を適用する。scope の中身は既存の `where('timestamp >= ? AND timestamp < ?', from, to + 1.day)` と同一で、`+1.day` の加算のみ scope 内部に閉じ込める。`@addresser` による絞り込みは現状のまま残す。

キャッシュキーは現在 `"uniq_count_by_destination_#{@addresser}"` のように addresser のみを含む。期間が結果に影響するようになる以上、キーにも `#{@recent_days_from}_#{@recent_days_to}` を含めなければ、本番環境で最初にアクセスした期間の集計結果が別の期間にも返る。これは機能追加ではなくバグ回避であり必須とする。

ビュー側では、期間を絞った結果 0 件になったときに `columns: []` の空チャートが描画される新しい失敗モードが生じる。Recently Bounced 側が既に採っている `<% if @count_by_destination.present? %>` のガード方式に揃える。

## 性能・品質・セキュリティ上の前提

性能面では悪化しない見込みである。Pi ではキャッシュが効かないため現状これら 4 クエリはダッシュボード表示のたびにテーブル全体を集約しており、期間で絞る方がスキャン量は減る。ただし推測に留めるべきで、遅い場合のみ Pi 上で `monitor_performance.rb` と `EXPLAIN` により実測してからインデックスを検討する。投機的なインデックス追加はしない。

品質保証の方針は、ローカルに MySQL が無く（CLAUDE.md の Local Environment Constraints）、既存テストも `test/controllers/status_controller_test.rb` の 1 本が存在しないルートを参照して stale な状態にあるため、自動テストによる検証は成立しない。Pi 上での実地確認と、SQL による突き合わせを検証手段とする。

セキュリティ上の新規の懸念はない。期間パラメータは既に `params[:from]` / `params[:to]` として `to_date` を通しており、今回追加する述語もバインド変数経由である。

## リスクと対策

最大のリスクは、キャッシュキー変更漏れが Pi 上のテストでは絶対に露見しないことである。`cache_if_production` は `Rails.env.production?` 以外で素通しになるため、キーが古いままでも Pi では正しい数字が出てしまう。対策として、キャッシュキーの変更はコードレビューによる読み合わせで担保し、動作観測に頼らない。

次に、Unique Recipient Bounced の意味が「全期間のユニーク受信者数」から「指定期間内のユニーク受信者数」に変わる点がある。`<%= uniq_recipient_count %> recipients` の表示だけでは全期間の数字と誤読される余地が残るため、論点 3 の回答に従い、セクション見出しに集計期間を明示して対策する。

三点目として、`shorten_stats` フラグはこれら 4 クエリが全期間集計で重いことを理由に導入された経緯がある。期間で絞ればその前提は弱まるが、今回はフラグの挙動を変えずに据え置く。

## 残決定事項（判断ポイント）

### 論点1: 期間述語の重複をどう扱うか

`where('timestamp >= ? AND timestamp < ?', @recent_days_from, @recent_days_to + 1.day)` は現在 4 箇所にあり、変更後は 8 箇所になる。CLAUDE.md の DRY 原則に照らすと集約したいが、集約すると既に動いている前半 4 ブロックにも手が入る。

- A. 8 箇所とも同じ式を素直に書く — 利点: 差分が後半 4 ブロックに閉じ、動いているコードを触らない。既存スタイルとの一貫性も保たれる / 欠点: 同じ式が 8 回現れ、将来境界条件を変えるときの修正漏れリスクが残る
- B. `BounceMail` に `scope :within_period, ->(from, to) { where('timestamp >= ? AND timestamp < ?', from, to + 1.day) }` を定義し 8 箇所すべてで使う — 利点: 述語が単一の情報源に集約され、上下セクションの境界がずれ得なくなる / 欠点: 差分が前半の動作確認済みブロックにも及び、検証範囲が広がる
- C. コントローラ内 private メソッド（`scoped_relation`）に addresser 絞り込みごと集約する — 利点: `relation = ...; relation = relation.where(addresser:) if ...` の定型 8 回分もまとめて消える / 欠点: 変更が最も大きく、`@bounced_by_type` など形の違うブロックに合わせる調整が要る
- D. その他（自由記述）

推奨: B。境界が 1 日ずれると上下のチャートが食い違って「データバグ」に見えるという今回のリスクに直接効き、前半への差分も機械的な置換に留まるため。

[Answer]: B

### 論点2: キャッシュの有効期限を揃えるか

前半 4 ブロックは 15 分、後半 4 ブロックは 2 時間の `expires_in` を持つ。後半が期間追従するようになると、to = 今日 のような範囲では同じ画面の上半分と下半分が最大 2 時間ずれた数字を表示しうる。

- A. 後半も 15 分に揃える — 利点: 1 画面内の数値の一貫性が保たれる / 欠点: 重いクエリの実行頻度が上がる（ただし Pi では元々キャッシュ無効なので実害は本番相当環境に限る）
- B. 2 時間のまま据え置く — 利点: 差分が最小 / 欠点: 期間指定した直後に古い数字が返り、上下で食い違って見える
- C. その他（自由記述）

推奨: A。期間を揃えるのが本タスクの目的なので、キャッシュ起因のずれを残すのは目的に反する。

[Answer]: A

### 論点3: Unique Recipient Bounced の表示文言

このセクションは名前も表示も「全期間のユニーク受信者」を前提にしている。期間追従後、`(N recipients)` が何の期間の数字なのかが画面から読み取れない。

- A. 文言は変えない — 利点: 差分ゼロ / 欠点: 全期間の数字と誤読される
- B. 見出しに期間を添える（例: `Unique Recipient Bounced (2026-07-27 〜 2026-08-10)`）— 利点: 誤読を防ぎ、他セクションにも同じ書式を展開できる / 欠点: 見出しが長くなる
- C. その他（自由記述）

推奨: B。ただし表示位置と書式は好みが出るため確認したい。

[Answer]: B
