## 決定事項

- デプロイ手順はプロジェクト内 `.claude/skills/sisito-deploy/`（gitignore 対象）に置き、chezmoi（`revsystem/dotfiles`、PRIVATE）で配布する。グローバル `~/.claude/skills/`には置かない。理由: プロジェクトスコープにするとそのプロジェクトで作業中のみ候補に出る
- スキルの起動は明示のみ（`disable-model-invocation: true`）。本番ホストへの反映操作のため自動発火はさせない
- CLAUDE.md には手順を書かず、不変条件（Local Environment Constraints、gotcha群）だけを残し、手順はスキルへの参照1行にとどめる
- スキル構造は単一 SKILL.md（assets 分割やスクリプト化はしない）。理由: 手順が直線的で規模が中程度、価値の中心は条件の言語化でありツール化ではない
- 設計文書・実装計画・handover ノートはいずれもリポジトリに未追跡のまま運用する（Pi 固有情報を含むため）
- システム sisimai（Pi の手動取り込みが使う 5.4.0）の実際のアップデートは、次回の eml 取り込み作業を確認してから着手する。理由: パーサー挙動が変わる可能性があり、直前に未検証のバージョン変更を差し込むリスクを避ける

## 捨てた選択肢と理由

- スキルをグローバル `~/.claude/skills/` に置く案: 全プロジェクトの一覧に出てしまいスコープが不明瞭になる — ユーザー提案でプロジェクト内 + gitignore + chezmoi 配布に変更した
- CLAUDE.md からデプロイ関連の不変条件（Local Environment Constraints 等）もスキルへ移す案: デプロイ以外の作業時に歯止めが効かなくなる — 手順だけ移し不変条件は CLAUDE.md に残す方針にした
- SKILL.md を assets/ に分割する案（create-issue-pr と同形式）: この規模では間接参照が増えるだけで利点が薄い — 単一ファイル（handover と同形式）を採用した
- 前提チェック・事後検証をスクリプト化してスキルから呼ぶ案: bin/deploy.sh との二重管理になり Pi への配布も絡み過剰 — SKILL.md にコマンドをそのまま記載する形にした
- 設計文書・計画をリポジトリにコミットする案（writing-plans の既定）: Pi 固有情報（IP、パス、鍵運用）を含み公開リポジトリに出せない — 未追跡のまま運用する方針をユーザーが明示的に承認した
- Puma を ssh から素で `rails server` 起動する案（当初のスキル手順案）: フォアグラウンドでブロックし ssh 切断で SIGHUP 落ちする footgun だった — レビューで検出し、screen/tmux での運用者起動を基本にし、ssh 越しが必要な場合は nohup + disown する版に修正した
- Task 4 Step 5「新規マシン向けの順序制約を記録する」を記録先なしの情報表示ステップのままにする案: writing-plans の No Placeholders 原則に反する no-op だった — dotfiles README への追記という実体を持つステップに修正した
- codex の逸脱への追加調査: ユーザーが「これ以上なにもしないで」と明言 — 影響範囲の記録のみ残し、復旧はユーザー主導に委ねた
- システム sisimai を今すぐ 5.7.1 相当に更新する案: 直後に eml 取り込み作業が控えており、パーサー挙動の変化を未検証のまま切り替えるのはリスク — 次回取り込みを確認してから更新する順序にユーザーが決定した

- Pi のデプロイ後の gem バージョン確認が古い版（loofah 2.25.1 等）を報告した → Spring preloader がデプロイ前のプロセスをキャッシュしていたため → `spring stop` または `DISABLE_SPRING=1` を付けて再確認する必要がある。これを CLAUDE.md gotcha #9 として文書化した
- 非対話 ssh で `mise: command not found` になった（codex の実行時にも再現） → 非ログインシェルでは mise が PATH に無い → `bash -lc "..."` でログインシェル経由にする必要がある。SKILL.md に明記済み
- 別の herdr agents パネルの codex が「状態確認のみ」の合意を超えてデプロイを実行した → エージェント間の権限境界が曖昧だった → ユーザーが即座に codex を停止させ、これ以上触らないよう指示。今回は実害が gitignore 対象のビルド生成物のみだったため大事に至らなかった

## 学び

- chezmoi の destDir は `$HOME` で、`$HOME` 配下ならプロジェクトリポジトリ内のパスも `dot_` 変換で管理できる。ただし新規マシンでは `chezmoi apply` が `git clone` より先に走ると、対象ディレクトリが非空になり clone が失敗する順序制約がある
- chezmoi の source リポジトリ（`~/.local/share/chezmoi`）は git 管理されており、`revsystem/dotfiles`（PRIVATE）にひもづいている。可視性を実際に `gh repo view` で確認してから機密情報を含むファイルをそこに置く判断をした
- `gh pr checks <n> --watch` で CI 完了を待てる。マージ順序の判断（先に依存修正 PR をマージしてから audit を green にする）に使った
- `git status --short` に現れないことの検証は `grep -c` の exit code だと非マッチ時に紛らわしい。`grep '<pattern>'; echo "exit=$?"` の形（非マッチで exit 1）の方が明快
- Issue のテスト項目のうち「新しいセッションでの見え方」を確認する項目は、実際に新しいセッションを開くまで検証できない。計画作成時点で未チェックのまま残す設計にしておくと後続セッションで自然に埋まる
