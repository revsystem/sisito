## 捨てた選択肢と理由

- postfix コンテナの自動バウンスデモループ（`a.b.c` 宛メール送信）でそのまま検証する案: サンドボックス環境に実 DNS が無く「Host not found, try again」の一時エラーが返り続け、ハードバウンスが永遠に生成されないため検証にならない — Postfix 形式の合成バウンスメールを直接 Maildir に投入する方式に変更
- ローカル配送失敗（`nonexistent-user@$(hostname)`）で DNS を迂回する案: 実際に試したが postfix 側の mydestination 設定等の要因でメールが正常にキューされず、追加の設定調査が必要になり時間対効果が悪い — 合成バウンスメール直接投入の方が確実で高速だったためそちらを採用
- `Dockerfile.sisito` の `.bundle/config` 欠落を `cp` 側で「無ければスキップ」に緩和する案: 表面上のエラーは消えるが実行時に deployment/path 設定が効かなくなる本質的な問題を隠すだけ — `BUNDLE_APP_CONFIG` を明示的に上書きして根本原因を解消する方式を採用
- postfix コンテナのビルド確認用に `docker-compose`（ハイフン版）コマンドを使う案: このマシンには `docker-compose` 単体バイナリが無く `docker compose`（v2 プラグイン）のみ利用可能だったため、CLAUDE.md のコマンド例修正は見送り、実際の検証はすべて `docker compose`（スペース）で実施した
- `docker compose build sisito 2>&1 | tail -N` で結果を確認する方式: パイプ経由だと `tail` の exit code (0) しか見えず、実際のビルド失敗を `echo EXIT=$?` で誤って成功と判定しかけた — 以降はファイルへリダイレクトして `echo EXIT=$?` を別行で追記する方式に変更した

## ハマりどころ

- `docker compose build sisito` が `bundle install` で exit code 5 → `Dockerfile.sisito` のベースイメージ（`ubuntu:jammy-20221003`）の apt ruby が 3.0.2 で `Gemfile.lock` の要求（ruby>=3.2.0、`connection_pool` 等）を満たせなかった → ベースイメージを `ruby:3.4.9-slim-bookworm` に変更して解決
- `gem install bundler mailcatcher bootstrap-sass` が sqlite3 のネイティブ拡張ビルドで失敗（`Could not configure the build properly (pkg_config)`）→ `pkg-config` パッケージが未インストール → apt install リストに追加して解決
- `RUN cp -a /tmp/sisito/.bundle /tmp/sisito/vendor /var/www/sisito/` が `No such file or directory` で失敗 → `ruby:*-slim-bookworm` イメージが `BUNDLE_APP_CONFIG=/usr/local/bundle` をグローバルに preset しており、`bundle config set --local` の書き込み先がプロジェクト直下からずれていた → ビルド時（`/tmp/sisito/.bundle`）・実行時（`/var/www/sisito/.bundle`）それぞれで `BUNDLE_APP_CONFIG` を明示的に上書きして解決
- `postfix` コンテナが `sisito:3000` への疎通待ちループで7分以上停止 → `mysql`/`postfix` だけ起動していて肝心の `sisito` コンテナを起動していなかった（`init.sh` の wait ループが原因） → `sisito` コンテナを実際に起動（一時的に Python の HTTP スタブで疎通確認 → 後に実物の `sisito` コンテナに差し替え）して解決
- `sisito` 再起動直後に `migrate.sh` が「Table 'bounce_mails' already exists」で失敗 → 検証用に手動作成していた簡易 `bounce_mails` テーブルが残っていた → `DROP DATABASE sisito_development` してから Rails の `db:create db:migrate` を最初から走らせて解決

## 学び

- `ruby:*-slim-bookworm` 系の公式イメージは `GEM_HOME` / `BUNDLE_PATH` / `BUNDLE_APP_CONFIG` をすべて `/usr/local/bundle` にグローバル preset している。プロジェクトローカルな `.bundle/config` を意図する構成では、ビルド時・実行時それぞれで `BUNDLE_APP_CONFIG` を明示的に上書きしないと静かに意図と異なる場所に書き込まれる
- 非推奨化された `bundle install --deployment` フラグは、新しい Bundler ではその場のインストール動作には反映されるが `.bundle/config` への永続化は行われなくなっている（`bundle config set --local deployment true` + `bundle config set --local path vendor/bundle` を明示的に呼ぶ必要がある）
- サンドボックス化されたネットワーク環境では、存在しない TLD への DNS 解決が NXDOMAIN（恒久エラー）ではなく「try again」（一時エラー）を返すことがあり、postfix はこれをハードバウンスではなく再試行対象として扱う。実 DNS に依存したバウンス生成デモは検証に使えないため、MTA 形式のバウンスメールを直接 Maildir に投入する手法が代替検証として有効
- `docker compose build ... | tail -N` はパイプの exit code が `tail` のものになり、実際のビルド失敗を隠してしまう。ファイルへのリダイレクト + 別行での `echo EXIT=$?` が確実
