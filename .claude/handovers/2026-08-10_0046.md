## 決定事項

- 期間述語は `BounceMail.within_period(from, to)` として scope に切り出し、上半分 4 箇所も含めて 8 箇所すべてで使う。`to + 1.day` の加算を scope 内部に閉じ込め、呼び出し側は素の `to` を渡す
- 期間述語は `where('timestamp >= ? AND timestamp < ?', from, to + 1.day)` から一切変えない。`<= to` や `end_of_day` に言い換えると上下のチャートが 1 日ずれる
- 下半分 4 ブロックのキャッシュキーに `#{@recent_days_from}_#{@recent_days_to}` を追加する（必須。機能追加ではなくバグ回避）
- 下半分の `expires_in` を 2 時間から 15 分に下げ、上半分と揃える
- 期間ラベルは `StatsHelper#stats_period_label(from, to)` に切り出し、Unique Recipient Bounced と Bounced by Type の見出し後ろにミュートテキストで置く（`Unique Recipient Bounced 2026-07-27 〜 2026-08-10 (37 recipients)` の形）。Recently Bounced は直下のフォームに from/to があるため対象外
- データが空のセクションに `No data in this period.` を 1 行出す。Unique 側は 3 ハッシュすべてが blank のときのみ
- 新規テストは追加しない。テスト基盤の整備（`sisito_test` の用意、stale テスト修正、CI へのテストジョブ追加）は別 Issue に切り出す
- `etc` 二重計上バグの修正は本タスクに含めない。別 Issue に切り出す
- 投機的なインデックス追加はしない。遅い場合のみ Pi で `monitor_performance.rb` と `EXPLAIN` を取ってから判断する
- `shorten_stats` フラグの挙動は変えない
- 実装は implement-verify-record スキルで、ユニットごとに承認ゲートを挟んで進める

## 捨てた選択肢と理由

- 期間述語を 8 箇所に素で書く案（spec 論点 1-A）: 同じ式が 8 回現れ、将来境界条件を変えるときの修正漏れリスクが残る — `BounceMail.within_period` scope に集約する案（B）を採用
- コントローラ private メソッド `scoped_relation` に addresser 絞り込みごと集約する案（spec 論点 1-C）: `@uniq_count_by_sender` と `@count_by_reason_date` は先頭が `select(...)` で形が異なり、統一に追加調整が要る — scope 化のみに留めた
- 下半分の `expires_in` を 2 時間のまま据え置く案（spec 論点 2-B）: 期間指定直後に上半分と最大 2 時間ずれた数字が出る — 15 分に揃える案（A）を採用
- 期間ラベルを括弧内にまとめる案（plan 論点 1-B）: Bounced by Type 側には `(N recipients)` が無く、2 セクションで括弧の中身の構造が揃わない — 見出し後ろにミュートテキストで置く案（A）を採用
- 期間ラベルをフォーム直下に 1 行だけ置く案（plan 論点 1-C）: 下までスクロールすると視界から外れ、「下半分も期間連動した」ことの誤読防止に弱い — 却下
- 空セクションを見出しごと非表示にする案（plan 論点 2-C）: `shorten_stats` でセクションが消える挙動と紛らわしい — `No data in this period.` を出す案（B）を採用
- `within_period` の引数を `to.to_date` で防御的に丸める案（Cursor Agent の示唆）: 現在の供給源は `params[:to].to_date` と `Date.today` の 2 つだけでどちらも Date。使われていない経路のために暗黙の型変換を入れると「切り捨てに気づかない」失敗に変質する — 契約をコメントで示すだけにした
- 下半分 4 系統すべてを SQL 突き合わせする案（Cursor Agent の提案）: `uniq_count_by_reason` は `uniq_count_by_destination` とチェーンの形が完全に同一で、片方が合えばもう片方も合う — destination / sender / bounced_by_type の 3 系統に絞った
- Recently Bounced の棒グラフ合計と Unique のドーナツ recipients 数を比較する検証手順（初稿にあった）: 前者は延べ件数、後者はユニーク受信者数で、さらに後者は `etc` 二重計上で膨らむため、正しい実装でも不等号が逆転しうる — 削除し、個別スライスと直接 SQL の突き合わせに置き換えた

## 学び

- `cursor-agent` CLI が `/home/tsuyoshi/.local/bin/cursor-agent` に入っており、`--print --mode ask --output-format text "<prompt>"` で read-only のレビューを非対話実行できる。プロンプトが長い場合はファイルに書いて `"$(cat file)"` で渡す。認証済みで追加設定なしに動いた
- `cache_if_production`（`app/controllers/application_controller.rb:25-33`）は `Rails.env.production?` のときだけ `Rails.cache.fetch` を通し、それ以外はブロックを素通しする。Pi は `RAILS_ENV=development` なのでキャッシュは実質無効。つまりキャッシュキーのバグは Pi 上の動作確認では絶対に検出できず、コードレビューでしか担保できない
- `_recent_bounced.html.erb` の `#count_by_date` チャートだけガードが無いのは、`stats_controller.rb:21` が `(from..to).map {|d| [d, cbd.fetch(d, 0)] }.to_h` で欠損日を 0 埋めしており Hash が常に非空になるため。他のチャートには `present?` ガードがある
- 空 Hash をチャートの columns 定型（`hash.to_a.slice(0,10).push(['etc', hash.values.slice(3..-1).try(:sum)]).select {|_,v| v.present? }`）に通すと `columns: []` になる。`[].slice(3..-1)` は `nil` を返し `nil.try(:sum)` → `nil` → `present?` で落ちるため。c3 は例外を投げず空チャートを描く
- `_bounced_by_type.html.erb` は `@bounced_by_type.sort_by(&:first).each_slice(4)` のループなので、空 Hash ならループが回らず JS のガードは不要
- パイ/ドーナツ 6 箇所すべてに `etc` 二重計上バグがある。`slice(0, 10)` で上位 10 件を個別表示しながら `etc` に `slice(3..-1)` の合計を入れているため、4〜10 件目が両方に計上されチャート合計が実数を超える。SQL と突き合わせるときは中央の合計ではなく個別スライスと比較する
- `config/application.rb:22` に `config.active_record.default_timezone = :local` があり、Pi は TZ=Asia/Tokyo。`bounce_mails.timestamp` は precision なし datetime で日付境界はローカル時刻で解釈される
- `config/database.yml` の test ブロックは `root` / パスワード無しで `sisito_test` を指すが、Pi での疎通は未確認
