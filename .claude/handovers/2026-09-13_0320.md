## 要対応・要判断（ユーザーの確認が必要）

### 1. PR #51のsquashコミット（マージ済み、master履歴）にセッションURLが残っている

`8362bbf`（`master`上、PR #51のsquashコミット）のコミットメッセージに `Claude-Session: https://claude.ai/code/session_...` トレーラが2箇所含まれている。ユーザーのグローバル `CLAUDE.md` は「セッションURLをPR本文・Issue本文・コミットメッセージのいずれにも含めない」と明記しており、これに反する。

w9:p2のレビューで発見（PR #53の本文に同じ問題があったのは修正済み）。**`master`の既存履歴を書き換える（rebase + force-push）操作なので、ユーザーの明示的な承認なしには実行していない。** 気にする程度の内容か（単なるメタデータ、秘密情報ではない）、直す場合は書き換えるか、を判断してほしい。Unit 5以降のコミット・PRでは既にこのトレーラを付けていない。

### 2. `bin/deploy.sh` が非対話SSHセッションで `mise: command not found` になる

`bin/deploy.sh` は内部で `mise install` / `mise exec --` を素の `mise` コマンドで呼んでいるが、非対話SSHセッションのPATHには `/home/pi/.local/bin` が含まれておらず失敗する（2026年8月の ingestion 停止事故と同じ種類のPATH問題）。今回は `export PATH="/home/pi/.local/bin:$PATH"` を前置して回避したが、スクリプト自体は直していない（Unit 5〜7と無関係な既存の別問題のため、今回のアップグレードのスコープには含めていない）。対応する場合は別Issueとして切り出すことを推奨。

## ハマりどころ

- `mise exec -- spring stop` は失敗する（`spring couldn't exec process`）。spring は mise管理のシェルコマンドではなくbundle経由のgem実行ファイルのため。`DISABLE_SPRING=1` を各コマンドに付ける方式に統一し、`spring stop` 自体は使わなかった
- Pi上で `mise exec -- ruby -v` をプロジェクトディレクトリ外から実行すると、mise.tomlが見つからずグローバルデフォルト（Ruby 3.2.3）に解決される。必ず `cd /home/pi/sisito`（またはworktree）してから実行する必要がある
- `gh pr merge --squash` はデフォルトで各コミットメッセージを連結する。セッションURLトレーラを含む可能性があるため、Unit 2以降は `--subject`/`--body` を明示指定してクリーンなメッセージに固定した

## 学び

- Pi検証の実際の手順は「マージ前に隔離git worktree（`git worktree add`、`bundle config set --local path <本体のvendor/bundle>` で共有）でboot確認 → マージ後に`bin/deploy.sh`で実配備・経路確認」の2段階が正しい。`bin/deploy.sh`が`master`からしかpullしないため、フィーチャーブランチを直接デプロイする方法は無い
- YJIT自動有効化やlog_file_size等、load_defaultsが引き上げるバージョンごとの影響は、Rails公式ソースコード（`configuration.rb`、`finisher.rb`等の該当タグ）を直接参照すれば確実に判定できる。Pi実機での`defined?`確認と組み合わせることで、researchフェーズの懸念を実装フェーズで機械的に解消できた
