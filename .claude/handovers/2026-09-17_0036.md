## 決定事項

- Unit 5（gemバンプ）だけは「事前宣言+diffレビュー」の高リスクゲートとし、ユーザー不在時には着手しない
- Pi検証の実施順序は「マージ前に隔離git worktreeでboot確認 → マージ後に`bin/deploy.sh`で実配備・経路確認」の2段階に統一する。`bin/deploy.sh`が`git pull --ff-only origin master`しかしないため、フィーチャーブランチを直接デプロイする方法が無いことに起因する運用ルール
- gemバンプを伴うUnit（5）のみ、隔離worktreeで共有`vendor/bundle`を使わず独自インストールし、隔離ポートで一時Pumaを起動して実HTTPリクエストとアセット配信まで確認する。config変更のみのUnitは共有`vendor/bundle`を参照するだけで十分とする
- `bin/deploy.sh`のmise PATH問題は、実行手順（毎回`export PATH`する）ではなくスクリプト自体に`export PATH="$HOME/.local/bin:$PATH"`を追加して恒久対応する（保守性優先、`bin/sync-and-ingest.sh`の過去の同種修正と同じ考え方）
- `gh pr merge --squash`は`--subject`/`--body`を明示指定する。指定なしだとブランチの各コミットメッセージがそのまま連結され、Claude-Sessionトレーラ等の意図しない内容が漏れる
- マージ済み`master`履歴の書き換え（force-push）は、ユーザーの明示的な許可が出た範囲（PR #51のみ）に厳密に限定する

## 捨てた選択肢と理由

- Rails 8.0を最終着地点にする案: セキュリティサポートが2026-11-07終了（アップグレード当時から約8週間後）と判明したため却下し、8.1を採用した
- `new_framework_defaults.rb`の`ssl_options`行を`production.rb`へ移設する案: `force_ssl`が未設定のためどの環境でも無効と判明し、移設不要と判断してファイルごと削除した
- Unit 1〜7を厳密に7 PRへ分割する代替案（Unit 1〜3をまとめて1 PRにする案）: ステージング無し環境では切り分け精度を優先し、7 PRのまま進めることを維持した
- PR#51以外の、この session 中に発見した過去のセッションURLトレーラ入りコミット（2025年7月〜2026年7月、複数のリリースタグが指す）を遡って修正する案: ユーザーから「過去のURLトレーラは無視します」と明示的に却下された。**今後もこれらの古いコミットには手を付けない**
- Unit 5実装後の複眼レビューを両ペインに毎回依頼する案: 1行差分のUnit 2・3・6・7では過剰と判断し、w9:p2単独レビューに留めた。複眼レビューはUnit 5（gemバンプ、最高リスク）とplan.md全体レビューにのみ使った

## ハマりどころ

- Pi上で`mise exec -- ruby -v`をプロジェクトディレクトリ外（`$HOME`）から実行 → プロジェクト指定のRuby 3.4.9ではなくグローバルデフォルト（3.2.3）が返る → 原因はmiseがカレントディレクトリの`mise.toml`しか見ないこと → 必ず`cd /home/pi/sisito`してから実行するよう徹底した
- `mise exec -- spring stop`が`couldn't exec process`で失敗 → springはmiseがシム管理する独立ツールではなくbundle経由のgem実行ファイルのため → `DISABLE_SPRING=1`を環境変数として渡す方式に統一し、`spring stop`自体は使わなかった
- Unit 5のPR作成直後、`bundle install`が一度だけ`mise`関連の不可解なエラーで失敗 → 原因不明のまま同じコマンドを再実行したところ完全にクリーンに成功（一過性の問題と判断し記録のみ残した）
- 履歴書き換え後force-pushしたら、Piのローカル`master`が旧履歴のままになり次回`bin/deploy.sh`の`git pull --ff-only`が失敗する状態になった → Piへ`ssh`して`git fetch && git reset --hard origin/master`で同期して解消

## 学び

- Rails本体のソースコード（`configuration.rb`、`finisher.rb`等の該当タグ）を直接`curl`で取得して確認すれば、load_defaultsの各バージョンで何が変わるかを推測でなく断定できる。Herdrペインのレビューでも同じ手法（RubyGems依存ページの直接参照）を使わせることで、二重の一次情報検証になった
- `initializer :enable_yjit`は`if config.yjit && defined?(RubyVM::YJIT.enable)`でガードされているため、YJIT非対応Rubyビルドではload_defaultsを上げても安全にno-opになる（Rails側の設計として、環境依存の機能は`defined?`ガードで守られている）
- 実装をw9:p2（Fable 5.1）、複眼レビューをw9:pA（Codex 5.3）という異なるモデルの組み合わせにしたことで、レビューが「同じ推論パターンの見落としを見逃す」リスクを減らせた。RubyGems依存ページという実装側とは異なる情報源からの裏取りが特に効いた
- `gh pr merge --squash`のデフォルト挙動（各コミットメッセージの連結）を把握していないと、`Co-Authored-By`や`Claude-Session`等のトレーラがブランチの個別コミットから最終的なmasterの履歴に意図せず引き継がれる
